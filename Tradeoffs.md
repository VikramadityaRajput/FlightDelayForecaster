After adding shared feature engineering, chronological splits, train-only priors, leakeage tests, I'm doing keeping track of my tradeoffs

The feature pipeline makes several deliberate tradeoffs in favor of simplicity. Historical delay rates by origin-hour, carrier and route are learned only from the training split and smoothed toward the overall average, so validation and test stay leak-free. But those rates are put back onto the same training rows they came from, which slightly inflates how useful they look during training. The fix is to compute each row's rate only from flights before it, at the cost of extra complexity. The data is split chronologically (70/15/15 by row count) instead of randomly, which reflects how a deployed model ages. It also means training covers winter (Nov–Feb) while testing covers March, so test scores are a realistic, slightly pessimistic estimate, and the month feature is unreliable because training never contains March. Weather in training comes from observed historical data, while the live API uses forecasts, so the model learns from cleaner weather than it gets in production. Training on archived historical forecasts would close that gap. Cancelled and diverted flights are dropped because they have no arrival delay to learn from, which likely makes the model underestimate risk on the most severely disrupted days. Finally, limiting the data to flights between 15 major hubs keeps data volume and weather API calls small, but anyone flying from a smaller airport can't get a prediction yet.

After Adding training/evaluation pipelines with ablation in scripts/train.py

The training pipeline makes a similar set of simplicity-first tradeoffs. Linear models (LogisticRegression and Ridge) use one-hot encoding and standard scaling so large-scale features like distance_miles don't dominate and unseen airports or carriers at inference don't crash the API, while LightGBM uses ordinal encoding with raw numeric features to avoid wide sparse matrices at the cost of treating categories as numeric splits rather than native categoricals. Class imbalance (~20% delayed flights) is handled with class_weight="balanced" and scale_pos_weight, and the decision threshold is tuned on the validation set to maximize F1 before freezing for test—which keeps test leak-free and boosts recall, though it pushes predicted probabilities upward (hurting calibration) and assumes equal cost between false alarms and missed delays across shifting monthly base rates. For delay-minute regression, LightGBM uses an L1 objective instead of squared error so rare 600-minute outliers don't skew typical predictions (MAE = 17.21 vs. Ridge's 20.81), trading slightly worse RMSE (56.33 vs. 53.35). Finally, using fixed hyperparameters without early stopping keeps training fast and reproducible but leaves a noticeable train-to-validation gap (0.4890 vs. 0.3078 PR-AUC), and the ablation confirms that keeping month (0.3848 vs. 0.3958 test PR-AUC without it) and reusing train-fitted priors in-sample (0.3848 vs. 0.3884 without them) hurt generalization on unseen months.

After deploying to AWS (SAM) and upgrading to the two-stage v2 model

Going live surfaced two practical tradeoffs. First, on the modeling side, the original v1 L1 regressor was trained on all flights—and because ~80% of flights arrive on time with ArrDelayMinutes = 0, it collapsed to predicting ~0.0 min even when the classifier predicted a 65%+ chance of delay. Switching to a two-stage (hurdle) setup fixed this: Stage 1 predicts P(delay >= 15 min) on all flights, and Stage 2 trains only on delayed flights to predict both severity buckets (15-45, 45-120, 120+ min) and conditional quantiles (p50/p90 on log1p delay). Because unobserved operational causes (late inbound aircraft, crew, ATC) still limit minute-level accuracy, surfacing bucket probabilities and a p50/p90 range is more honest than a single minute estimate while beating naive delayed-flight baselines (test bucket macro-F1 0.2907 vs. 0.2273; conditional p50 MAE 46.17 vs. 47.06).

Second, on the serving side, the Predict Lambda packages the model artifacts directly inside the ARM64 container image (MODEL_DIR) instead of downloading them from S3 on every cold start—trading faster, simpler startup and self-contained deployments for needing a container rebuild when releasing a new model version (with S3 kept as a versioned archive). To stay within AWS Free Tier, the API is unauthenticated but protected by API Gateway throttling (5 req/s, burst 10), CORS is restricted to the GitHub Pages origin, CloudWatch log retention is capped at 14 days, and raw weather snapshots expire after 30 days. The tradeoff for serverless scale-to-zero is cold-start latency after idle vs. ~200-250 ms warm, which we mitigated by raising Lambda timeout to 30s and memory to 1769 MB (1 full vCPU).
